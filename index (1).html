Labs

Security Fix Demonstrations

Each lab walks through one vulnerability found in the insecure version and the corresponding fix applied in the secure version.

Fix 1 · Authentication

Login Test — Password Hashing

Demonstrates that plaintext passwords are replaced with salted password hashes, so login no longer exposes or stores credentials in readable form.

Reflection: Testing the login flow showed me how a hashing scheme turns a stolen database into a much lower-value target. It reinforced that password storage is the first control, not the last.
Fix 2 · Local Storage

Data 1 — Encrypted Local Storage

Sensitive local data is moved from plain SharedPreferences into EncryptedSharedPreferences, preventing casual extraction from a rooted or backed-up device.

Reflection: Comparing the two storage approaches made the risk tangible. I learned that data at rest on a mobile device is never as private as developers assume, so encryption must be on by default.
Fix 3 · Transport

Data 2 — HTTPS / TLS Transmission

Network calls are switched from cleartext HTTP to HTTPS with TLS, protecting credentials and session data while they travel between the app and the backend.

Reflection: Watching traffic on the wire exposed how easy it is to intercept unencrypted requests. This lab drove home that transport security is just as important as storage security.
Fix 4 · Injection

SQL Injection — Parameterized Queries

Search and login queries are rewritten as parameterized statements, so malicious input can no longer alter the SQL structure and extract or modify data.

Reflection: Crafting an injection payload that bypassed the insecure search was eye-opening. After switching to parameterized queries, the same payload became harmless input — a clear demonstration of defence in depth.
Projects

Secure Student Management System

Two iterations of the same Android application: the intentionally insecure baseline, and the hardened version that fixes the four demonstrated vulnerabilities.

Insecure Baseline

Secure Student Management System — Insecure Version

The initial version lacks security controls: passwords are stored in plaintext, data is kept in insecure local storage, traffic is sent over insecure transmission, and queries are vulnerable to SQL injection.

Reflection: Building the insecure version first let me experience how each flaw is exploited from an attacker's point of view. It showed me that convenience shortcuts during early development become real vulnerabilities later.
View on GitHub
Hardened Version

Secure Student Management System — Secure Version

Based on the initial version, this release fixes the four vulnerabilities by adding password hashing, encrypted local storage, HTTPS transport, and parameterized SQL queries.

Reflection: Re-applying the same attack steps against the secure version — and watching them fail — was the most convincing part of the project. It proved that layered controls actually change the outcome, not just the code.

Reflection

What I Learned

Through this project, I learned how to apply security principles to a real Android application — especially input validation, password storage, access control, and audit logging. I also learned that security cannot rely on a single measure; it requires defence in depth and continuous testing.

When using AI to generate HTML and review code, I learned that I must verify every piece of code and every link instead of trusting the output blindly. This learning process has made me more confident in prioritising security in future development.
